# 自律健身 App — 产品需求文档（PRD）

> 版本：v1.0 ｜ 形态：简单 PRD（MVP 冻结）｜ 作者：许清楚（产品经理）
> 定位：**个人自用 · 单机离线 · 安卓原生**

---

## 1. 项目信息

| 项目 | 内容 |
|------|------|
| 文档语言 | 简体中文 |
| 编程语言 / 技术栈 | Kotlin + Jetpack Compose + Material 3 + MVVM + Room + Hilt（纯原生，与全部参考项目一致） |
| 项目名称（snake_case） | `iron_habit`（App 显示名待定，暂用「自律健身」） |
| 代码基座 | 开源项目 **BaseFit**（MIT）为骨架，融合 MysLog / Lift / Gritly 等 MIT 项目优点；Habitized（GPL-3.0）**仅借鉴产品玩法，不复制代码** |
| 构建方式 | 本机无 JDK/Android SDK → 通过 **GitHub Actions 云端 CI 自动构建并签名 APK** |
| 运行平台 | 仅 Android（minSdk 24 / target 34） |
| 商业模式 | 无（个人自用，不上架、无账号、无广告、无内购） |

### 原始需求复述

> 用户想要一个**自律健身的个人 App，需在安卓端运行**。以 BaseFit 为骨架改造并融合其他开源项目优点；采用 Kotlin + Compose + Room 原生栈；因本机无 Android 构建环境，APK 通过云端 CI 自动构建签名；面向个人自用，单机离线优先，无账号无广告。
>
> 核心诉求是**双重**的：既要「**想练**」（有计划地训练并记录），也要「**想坚持**」（用连续打卡、提醒、计时把自律变成习惯）。因此本 App 不是单纯的健身记录工具，也不是单纯的打卡工具，而是**把训练动作作为"可打卡的习惯"来运营**的自律系统。

## 2. 产品定义

### 2.1 一句话目标

**把一个容易断档的健身意愿，变成每天"打开 App → 看到今天该做什么 → 一键勾掉 → 连续记录不断"的零摩擦闭环。**

### 2.2 产品目标（3 个正交目标）

| # | 目标 | 衡量方式（可度量） |
|---|------|-------------------|
| G1 | **让"想练"可执行**：把模糊的健身意愿，拆成"今天具体练哪几个动作、做几组几次"的可执行清单 | 打开 App 到看到今日训练 ≤ 1 次操作（0 跳转）；一次训练打卡 ≤ 3 次点击完成 |
| G2 | **让"想坚持"有反馈**：用连续打卡、时长、进度条、成就形成正反馈，抑制断档 | 首页首屏可见当前 streak 与今日完成进度；streak 断档/连击有明确视觉状态 |
| G3 | **让"记录"零负担**：全程离线、无账号、无网络依赖，本地即数据、即隐私 | 飞行模式下 100% 功能可用；杀进程重开数据不丢；0 个需要登录的入口 |

### 2.3 目标用户与画像

| 维度 | 描述 |
|------|------|
| 用户规模 | **1 人**（用户本人），单设备、单用户，无多账号 |
| 身份 | 有健身意愿、但在"坚持"上容易断档的成年人；非专业运动员，训练以自重 / 力量 / 有氧为主 |
| 设备 | 一台安卓手机（Android 7.0+），训练时随身携带 |
| 核心痛点 | ① 不知道自己"今天该练什么"；② 记录靠脑子/备忘录，训练后懒得记；③ 练了几天就断，没有"断不掉"的约束感；④ 讨厌注册、广告、付费墙 |
| 使用场景 | 健身房 / 家中 / 训练间隙，多数为**单手、短时间内**操作；常在无网络或不想联网的场景 |
| 期望 | "打开就能练、点一下就算记完、断了我自己会心疼"——把自律外包给一个不会说教的工具 |

### 2.4 用户故事

**A. 训练线（"想练"）**

1. *As* 训练中的我，*I want* **为一周 7 天分别安排要练的动作和目标组数/次数**，*so that* 打开首页就知道今天该做什么，不用临时想。
2. *As* 训练完的我，*I want* **对已完成动作一键打卡，并顺手记录实际组数、次数（可选重量/时长/备注）**，*so that* 记录不成为负担，练完即记完。
3. *As* 想看到进步的我，*I want* **查看每个动作 / 每周 / 每月的完成趋势图**，*so that* 我能直观看到自己在变强，而不是凭感觉。

**B. 自律线（"想坚持"）**

4. *As* 想养成习惯的我，*I want* **把"每天训练""每天喝水/拉伸"这类行为设成可勾选的每日/每周习惯，并显示连续打卡天数**，*so that* 有"连续不能断"的约束感和成就感。
5. *As* 容易忘事的我，*I want* **到点收到本地提醒、训练时能用休息倒计时控制节奏**，*so that* 不用靠自制力硬扛时间和节奏，降低断档概率。

## 3. 技术规范

### 3.1 需求池（P0 / P1 / P2）

> **优先级约定**：P0 = MVP 必须有（Must，且**必须纯本地离线可实现**）；P1 = 重要（Should）；P2 = 以后再说（Nice to have）。
> **硬约束**：P0 的所有功能不得引入任何需要服务器、账号或联网的能力。

#### P0 — MVP 必须（纯本地离线）

| 编号 | 功能 | 说明 | 验收标准（一句话） |
|------|------|------|-------------------|
| P0-1 | **动作库** | 内置常见自重/力量/有氧动作，按分类浏览；支持自建动作 | 首次启动即含 ≥40 个内置动作，可按分类筛选，可新增/编辑/停用自定义动作 |
| P0-2 | **周训练计划** | 为周一~周日分别配置动作与目标组数/次数 | 可为任意一天新增/编辑/删除计划条目；首页按"今天是周几"自动展示对应计划 |
| P0-3 | **今日视图 + 一键打卡** | 展示今日计划与完成进度；点击即完成打卡 | 点击打卡后当天该动作标记为已完成；可补录组数/次数/重量（可选）；首页显示"已完成 x / 共 y"与进度条 |
| P0-4 | **习惯追踪** | 自定义每日/每周习惯，逐日勾选 | 可新建/编辑/删除习惯；勾选状态当天持久化，重启后仍保留 |
| P0-5 | **连续打卡 streak** | 计算当前连续天数与历史最长天数 | 连续打卡 +1、断档归 0、历史最长值永久保留；首页首屏可见当前 streak |
| P0-6 | **统计图表** | 完成趋势 + 分类分布 | 至少 2 张图（近 30 天打卡趋势折线/柱状、动作分类占比），离线渲染、数据变化自动刷新 |
| P0-7 | **本地持久化（Room）** | 全部数据本地存储 | 杀进程/重启手机后数据完整不丢；无任何写入网络的调用 |
| P0-8 | **本地通知提醒** | 训练/习惯的每日提醒 | 可设定提醒时间；到点触发**本地**通知（无网络依赖）；可开关 |
| P0-9 | **打卡历史视图** | 查看过往每日完成记录 | 可按日期浏览历史，展示当天完成/未完成项与完成率 |

#### P1 — 重要（Should）

| 编号 | 功能 | 说明 | 验收标准 |
|------|------|------|---------|
| P1-1 | **休息计时器** | 组间倒计时 | 可设定秒数并倒计时，结束有声音/通知提示，可在后台运行 |
| P1-2 | **番茄钟 / 计时习惯** | 面向"专注/时长类"习惯 | 可对某个习惯启动正计时/倒计时，完成后自动记为一次打卡 |
| P1-3 | **成就 / 里程碑** | 连击、累计次数等徽章 | 达成阈值时点亮徽章并有一次性提示；进度可见 |
| P1-4 | **身体数据记录** | 体重/体脂等趋势 | 可按日期录入并查看趋势曲线（纯手填，不接任何健康平台） |
| P1-5 | **数据导入 / 导出** | 换机与防丢 | 可导出为本地 JSON 文件并导入恢复，过程完全离线 |
| P1-6 | **深色模式 / 主题** | 跟随系统或手动 | 主题可切换且重启后保持 |
| P1-7 | **单位切换** | 公制 / 英制 | 重量与长度单位可切换，全局即时生效 |

#### P2 — 以后再说（Nice to have）

| 编号 | 功能 | 说明 |
|------|------|------|
| P2-1 | 预设挑战计划 | 如"30 天俯卧撑挑战"等成套模板（BaseFit 已有类似能力） |
| P2-2 | 动作媒体 / 拍照记录 | 为动作配图/GIF、训练打卡拍照留档 |
| P2-3 | 桌面小组件 / 快捷打卡 | 桌面直达今日打卡 |
| P2-4 | 多语言 | 至少中/英 |
| P2-5 | 待办清单 | 与习惯打通的轻量待办（Habitized 玩法） |
| P2-6 | 云同步 / 多设备 | **仅在用户明确需要时再评估**（会打破"纯本地"约束） |
| P2-7 | iOS 版 | 需另起技术方案 |

### 3.2 页面结构推荐（底部导航）

**推荐方案：4 个底部 Tab**（个人自用，减少层级、聚焦核心闭环）

| Tab | 名称 | 定位 | 覆盖需求 |
|-----|------|------|---------|
| 1 | **今日** | 今天的训练 + 习惯 + 进度，一屏搞定 | P0-3 / P0-4 / P0-5 |
| 2 | **训练** | 周计划管理 + 动作库 + 打卡历史 | P0-1 / P0-2 / P0-9 |
| 3 | **自律** | 习惯列表 + 连续记录 + 日历热力图 | P0-4 / P0-5 |
| 4 | **我的** | 统计图表 + 身体数据 + 设置/导出 | P0-6 / P1-4 / P1-5 / 设置 |

> 备选：沿用 BaseFit 的 5 Tab（首页 / 计划 / 记录 / 统计 / 我的）。**建议先上 4 Tab**，把"习惯"与"训练"在「今日」页合并呈现，更贴合"自律+健身一体"的产品定位。

### 3.3 UI 设计稿描述（逐屏）

**通用约定**：Material 3 组件；底部导航常驻；顶部使用 TopAppBar；所有写入操作给 Snackbar 反馈。

#### Tab 1 · 今日（默认首页）
- **顶部**：日期 + 问候语；右上角设置入口。
- **核心卡片 · 今日进度环**：显示"已完成 3 / 共 5"进度环或进度条；下方大字显示**当前 streak（🔥 连续 N 天）**。
- **今日训练区**：卡片列表，每张含 动作名 + 分类标签 + 目标"3 组 × 15 次" + 右侧**一键打卡按钮**；已完成项置灰打勾并下移。
- **今日习惯区**：习惯勾选列表（复选圆圈），勾选即完成当天打卡。
- **空态**：无今日计划 → 插画 + 「今天没有安排，去添加计划」按钮直跳 Tab2。
- **加载态**：骨架屏（骨架卡片 ×3）。
- **错误态**：顶部 Snackbar + 「重试」（本地数据几乎不报错，仅作兜底）。

#### Tab 2 · 训练
- **子分区/顶部分段**：`周计划` / `动作库` / `历史`。
- **周计划**：周一到周日横向日历条，选中某天列出当天动作；FAB「+」新增计划条目（选动作 → 设组数/次数）。
- **动作库**：分类筛选栏（自重 / 力量 / 有氧 / 自定义）+ 动作列表；点条目进详情；FAB「+」新增自定义动作。
- **历史**：按日期倒序的记录列表，每条显示日期、完成项与完成率。
- **空态**：计划为空 → 「还没有计划，添加第一个动作」；库无自定义 → 「内置动作可直接使用」。
- **加载态**：列表骨架屏。
- **错误态**：整页错误占位 + 重试按钮。

#### Tab 3 · 自律
- **习惯列表**：每个习惯一行，含名称、频率（每日/每周几）、**当前 streak**、今日勾选态。
- **日历热力图**：类 GitHub 贡献图，按天展示打卡密度，颜色越深连续越久。
- **统计小结**：本月完成率、最长连击。
- **空态**：无习惯 → 「创建第一个习惯，开始积累连续天数」。
- **加载态**：热力图骨架块。
- **错误态**：占位 + 重试。

#### Tab 4 · 我的
- **统计图表**：近 30 天打卡趋势图 + 动作分类占比图（Vico 或同类库）。
- **身体数据**：体重/体脂等记录入口与趋势（P1）。
- **设置列表**：提醒时间、主题（浅/深/跟随系统）、单位（公制/英制）、数据导出/导入、关于。
- **空态**：无数据 → 「完成一次打卡后这里会出现趋势」。
- **加载态**：图表占位骨架。
- **错误态**：图表区错误提示 + 重试。

#### 二级页面
- 新增/编辑计划页、动作详情页、打卡详情页、身体数据录入页、数据导出/导入页——均为标准表单页，含顶部返回、必填校验、保存按钮禁用态。

### 3.4 范围与约束（明确"不做"）

| 约束 | 说明 |
|------|------|
| 离线优先 | P0 全部功能离线可用；不引入任何网络请求 SDK |
| 无账号 | 无登录、无注册、无用户体系 |
| 无商业化 | 无广告、无内购、不上架应用商店 |
| 单用户单设备 | 数据模型按单用户设计，不做多账号隔离 |
| 许可合规 | 代码基座用 **MIT**（BaseFit / MysLog / Gritly / Lift）；**GPL-3.0 的 Habitized 等只借鉴玩法与交互，不复制代码** |
| 构建 | 不要求本机具备 JDK/Android SDK，交付以云端 CI 产出的**已签名 APK**为准 |

## 4. 待确认问题（Open Questions）

| # | 问题 | 影响 | 我的默认假设（未拍板前按此执行） |
|---|------|------|-------------------------------|
| Q1 | 是否需要**登录 / 云同步**？ | 决定是否要引入后端与账号体系 | **不需要**，纯本地离线 |
| Q2 | 动作库是**内置**、**用户自建**，还是**两者都要**？ | 影响 P0-1 工作量与数据预置 | **两者都要**：内置 ≥40 个 + 允许自建 |
| Q3 | 打卡记录粒度：只记"完成"，还是要记 **组 × 次 × 重量**？ | 决定数据模型复杂度与统计能力 | 记**组/次/重量（重量可选）**，默认一键完成、可选展开补录 |
| Q4 | "习惯"与"训练"是**合并成一个列表**还是**两条独立线**？ | 影响首页与导航结构 | **首页合并呈现、后台分两线管理**（见 3.2） |
| Q5 | 是否需要**数据导出/备份**以防换机丢失？ | 决定 P1-5 优先级 | 列为 **P1**，用本地 JSON 导出/导入 |
| Q6 | 是否需要 **iOS** 版本？ | 决定技术选型是否要跨端 | **仅 Android** |
| Q7 | 休息计时器/番茄钟是否算 MVP 必须？ | 决定其优先级 | 列为 **P1**（提升体验但非核心闭环） |
